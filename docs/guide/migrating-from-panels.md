# Migrating from `@pilotiq/panels` to `@pilotiq/pilotiq`

`@pilotiq/panels` is being sunset and replaced by `@pilotiq/pilotiq` (the new view-based admin builder). This guide is the practical map: how panels concepts translate, what stays the same, what changes, and the order to migrate one resource at a time.

> **Scope:** free packages only. Pro features (`@pilotiq-pro/{collab,ai,workspaces}`) are not covered here — they re-attach to the new pilotiq separately.

---

## Conceptual changes (read this first)

| Area | Panels (legacy) | Pilotiq (new) |
|---|---|---|
| Resource methods | **Instance** methods (`fields()`, `filters()`, `actions()`) | **Static** methods (`form()`, `table()`, `detail()`) — Resources register as classes, not instances |
| Form vs table | Single `fields()` array, fields auto-render in both | Form and Table are separate elements with their own schemas |
| Page wiring | Vendored React pages copied via `pnpm rudder vendor:publish --tag=pilotiq-pages` | Auto-generated by a `pilotiq()` Vite plugin from the registered resources |
| Routing | Resources mount under `/{panel}/resources/{slug}` | Resources mount under `{base}/{slug}` (no `/resources` segment) |
| Provider | `panels()` provider with config object | Two lines: `pilotiq()` Vite plugin + `pilotiq([panels])` provider |
| Rich text | `RichContentField` (Lexical) | `RichTextField` from `@pilotiq/tiptap` (Tiptap) |
| Page hierarchy | Single Page concept | Optional `ListPage` / `CreatePage` / `EditPage` / `ViewPage` base classes |

The biggest mental shift: **fields no longer auto-populate the table.** You declare form schema and table columns explicitly.

## Setup

### Panels

```ts
// bootstrap/providers.ts
import { panels } from '@pilotiq/panels'

panels({
  panels: [adminPanel],
  // …
})
```

```bash
pnpm rudder vendor:publish --tag=pilotiq-pages --force
```

### Pilotiq

```ts
// vite.config.ts
import { pilotiq } from '@pilotiq/pilotiq/vite'

export default defineConfig({
  plugins: [pilotiq(), /* … */],
})
```

```ts
// bootstrap/providers.ts
import { pilotiq } from '@pilotiq/pilotiq'
import { adminPanel } from '../app/Pilotiq/adminPanel.js'

pilotiq([adminPanel])
```

No vendoring step. The Vite plugin generates `pages/(pilotiq)/` stubs that wrap the registered panels.

## Migrating a Resource

### Panels

```ts
// app/Panels/Admin/resources/ArticleResource.ts
import { Resource, TextField, SelectField, SelectFilter, Action } from '@pilotiq/panels'
import { Article } from '../../Models/Article.js'

export class ArticleResource extends Resource {
  static model         = Article
  static label         = 'Articles'
  static labelSingular = 'Article'
  static titleField    = 'title'

  fields() {
    return [
      TextField.make('title').required().searchable().sortable(),
      TextField.make('slug').required().searchable(),
      SelectField.make('status').options(['draft', 'published']).required(),
    ]
  }

  filters() {
    return [
      SelectFilter.make('status').options([
        { label: 'Draft',     value: 'draft' },
        { label: 'Published', value: 'published' },
      ]),
    ]
  }

  actions() {
    return [
      Action.make('publish').label('Publish').handler(async (records) => { /* … */ }),
    ]
  }
}
```

### Pilotiq

```ts
// app/Pilotiq/Articles/ArticleResource.ts
import {
  Resource, Form, Table, Column,
  TextField, SelectField, SelectFilter, Action,
} from '@pilotiq/pilotiq'
import { Article } from '../../Models/Article.js'

export class ArticleResource extends Resource {
  static override label         = 'Articles'
  static override labelSingular = 'Article'
  static override model         = Article

  static override form(form: Form): Form {
    return form.schema([
      TextField.make('title').required(),
      TextField.make('slug').required(),
      SelectField.make('status').options([
        { label: 'Draft',     value: 'draft' },
        { label: 'Published', value: 'published' },
      ]).required(),
    ])
  }

  static override table(table: Table): Table {
    return table
      .columns([
        Column.make('title').sortable().searchable(),
        Column.make('slug').searchable(),
        Column.make('status').sortable(),
      ])
      .filters([
        SelectFilter.make('status').options([
          { label: 'Draft',     value: 'draft' },
          { label: 'Published', value: 'published' },
        ]),
      ])
      .defaultSort('createdAt', 'desc')
      .paginate(15)
  }
}
```

### What changed

1. **`fields()` → `static form(form)`** — note the `static`. Returns the configured `Form` element.
2. **Table columns are explicit.** Use `Column.make(name)` per visible column, not field declarations. Move `searchable()` / `sortable()` from the field to the column.
3. **Filters move into `table().filters([…])`** — they're a Table concern, not a top-level Resource concern.
4. **Actions are part of either the table (header/bulk/row), the form (submit/cancel), or page headers** (covered below). There's no top-level `actions()` method.
5. The model-backed defaults still kick in: setting `static model = Article` auto-wires `Form.save / loadRecord / Resource.deleteRecord / Table.records`. Override any of them to take control.

### Register on the panel

```ts
// app/Pilotiq/adminPanel.ts
import { Pilotiq } from '@pilotiq/pilotiq'
import { ArticleResource } from './Articles/ArticleResource.js'

export const adminPanel = Pilotiq.make('Admin')
  .path('/admin')
  .resources([ArticleResource])
```

## Form lifecycle hooks

The lifecycle for a form submit runs in a fixed order. Mode-specific hooks
(create vs update) layer on top of the generic ones, so cross-cutting logic
(audit fields, auth stamping) can sit above mode-specific business rules.

```
validateSchema
  → form-level validators
  → mutateData (both modes)
  → mutateDataBeforeCreate / mutateDataBeforeUpdate
  → beforeSave (both modes)
  → beforeCreate / beforeUpdate
  → handleCreate || handleUpdate || save     ← persistence
  → afterCreate / afterUpdate
  → afterSave (both modes)
  → redirectAfterSave
```

The edit-mode load path runs:

```
loadRecord
  → mutateFormDataBeforeFill
  → fillFromRecord
  → mutateFormDataAfterFill
  → form.withValues(...)
```

You can configure hooks at either of two layers — they compose the same
form internally, so pick whichever fits the resource.

### Layer 1: `Resource.form()` (programmatic)

```ts
static form(form: Form): Form {
  return form
    .schema([…])
    .mutateFormDataBeforeFill((values, ctx) => {
      // ctx.record is the loaded record
      return { ...values, tagsCsv: (ctx.record.tags ?? []).join(', ') }
    })
    .beforeUpdate(async (data, ctx) => {
      data.editedBy = ctx.user?.id
    })
    .afterUpdate(async (record) => { await invalidateCache(record.id) })
    .savedNotification('Article saved')
}
```

All `Form` setters: `mutateData / mutateDataBeforeCreate / mutateDataBeforeUpdate`,
`beforeSave / beforeCreate / beforeUpdate`, `save / handleCreate / handleUpdate`,
`afterSave / afterCreate / afterUpdate`, `redirectAfterSave`,
`loadRecord / fillFromRecord / mutateFormDataBeforeFill / mutateFormDataAfterFill`,
`savedNotification / createdNotification / disableSavedNotification`.

### Layer 2: page-class overrides (Filament-style)

`CreatePage` and `EditPage` expose the same hooks as static methods. They
install onto the form during `schema()`, layering on top of whatever
`Resource.form()` configured.

```ts
class EditArticle extends EditPage {
  static override getResource() { return ArticleResource }

  static override beforeUpdate = async (data) => {
    data.updatedAt = new Date()
  }

  static override getSavedNotificationTitle() {
    return 'Article updated'   // overrides the default "Article saved"
  }

  static override getRedirectUrl = (record) => `articles/${record.id}/edit`
}
```

Override surface on `CreatePage`: `mutateFormDataBeforeFill / AfterFill`,
`mutateData / mutateDataBeforeCreate`, `beforeSave / beforeCreate`,
`afterSave / afterCreate`, `handleCreate`, `getRedirectUrl`,
`getCreatedNotificationTitle`. `EditPage` mirrors with `…BeforeUpdate`,
`handleUpdate`, `getSavedNotificationTitle`.

### Notifications

A successful submit auto-emits a success toast unless you opt out:

- `Resource.labelSingular` "created" on the create page (default)
- `Resource.labelSingular` "saved" on the edit page (default)
- Override the title with `getCreatedNotificationTitle()` /
  `getSavedNotificationTitle()` on the page, or
  `Form.createdNotification(...)` / `savedNotification(...)`.
- Return `null` from the page hook (or call `Form.disableSavedNotification()`)
  to suppress the toast for that mode.

> **Note:** delivery uses two paths depending on the request style.
> Action-modal submits (fetch + `Accept: application/json`) carry
> notifications inline in the JSON response. Browser-style form-post
> submits (303 redirect) persist them across the redirect via
> `@rudderjs/session`'s flash primitive — pilotiq writes
> `req.session.flash('pilotiq:notifications', ...)` on POST, reads on
> the next GET, and merges into `viewProps.notifications`. If the host
> app hasn't installed `@rudderjs/session`, the 303 path silently drops
> the toast (no error); add the session provider to enable delivery.

### Mapping from panels

| Panels                                | Pilotiq                                          |
|---|---|
| `mutateData(data)`                    | `Form.mutateData(fn)` or `static mutateData = fn` |
| `beforeSave(data)`                    | `Form.beforeSave(fn)` / page `beforeSave`         |
| `afterSave(record)`                   | `Form.afterSave(fn)` / page `afterSave`           |
| `redirectAfterSave(record)`           | `Form.redirectAfterSave(fn)` / page `getRedirectUrl` |
| `mutateFormDataBeforeFill(values)`    | `Form.mutateFormDataBeforeFill(fn)` / page hook   |
| (no separate create/update hooks)     | `beforeCreate / beforeUpdate / handleCreate / handleUpdate` |

## Field type mapping

Most field types carry over with the same API. The `Field` builder, `.required()`, `.placeholder()`, `.label()`, etc. are unchanged.

| Panels | Pilotiq |
|---|---|
| `TextField`     | `TextField` |
| `EmailField`    | `EmailField` |
| `NumberField`   | `NumberField` |
| `SelectField`   | `SelectField` |
| `TextareaField` | `TextareaField` |
| `ToggleField`   | `ToggleField` |
| `DateField`     | `DateField` |
| `SlugField`     | `SlugField` |
| `RichContentField` (Lexical) | `RichTextField` from `@pilotiq/tiptap` |

**Visibility flags** (`hideFromTable`, `hideFromCreate`, `hideFromEdit`, `hideFromView`, `showWhen`, `hideWhen`, `disabledWhen`) work the same way.

**Validation** is now via `.validate(rule | rule[])` with built-in helpers (`required()`, `email()`, `minLength()`, `maxLength()`, `min()`, `max()`, `pattern()`). `Field.required()` still works as a shorthand and auto-contributes a `required()` validator.

### Rich text

```ts
// panels (legacy)
RichContentField.make('body').blocks([Callout])

// pilotiq
import { RichTextField, Block } from '@pilotiq/tiptap'

RichTextField.make('body').blocks([
  Block.make('callout').schema([…]),
])
```

`@pilotiq/tiptap` ships its own `Block` builder mirroring the panels API. Wire the renderer once on the client:

```ts
// app/bootstrap.ts
import { registerTiptap } from '@pilotiq/tiptap/register'
registerTiptap()
```

## Pages

In panels, pages were vendored React files you edited in `pages/(panels)/`. In pilotiq, pages are **classes** that extend one of four base classes. The Vite plugin generates Vike route stubs that dispatch to them.

### Default — no page classes needed

For the standard list / create / edit / view CRUD, just define the Resource. The `pilotiq()` Vite plugin auto-generates the four pages.

### Custom — folder-per-resource layout

For per-page customization (custom headers, extra actions, custom save logic), break out one Page subclass per role:

```
app/Pilotiq/Articles/
├── ArticleResource.ts
├── Pages/
│   ├── ListArticles.ts      # extends ListPage
│   ├── CreateArticle.ts     # extends CreatePage
│   ├── EditArticle.ts       # extends EditPage
│   └── ViewArticle.ts       # extends ViewPage
├── Schemas/
│   └── ArticleForm.ts       # Form configuration helper (optional)
└── Tables/
    └── ArticlesTable.ts     # Table columns + actions (optional)
```

Each page is a one-liner unless you need to override:

```ts
// Pages/ListArticles.ts
import { ListPage } from '@pilotiq/pilotiq'
import { ArticleResource } from '../ArticleResource.js'

export class ListArticles extends ListPage {
  static override getResource() { return ArticleResource }
}
```

Wire them via `Resource.pages()`:

```ts
export class ArticleResource extends Resource {
  // …
  static override pages() {
    return {
      list:   ListArticles,
      create: CreateArticle,
      edit:   EditArticle,
      view:   ViewArticle,
    }
  }
}
```

Override hooks available per page:

| Page | Hooks |
|---|---|
| `ListPage` | `getHeader(R)`, `getHeaderActions(R, basePath)`, `getRowActions(R, basePath)` |
| `CreatePage` | `getHeader(R)`, `getFormActions(R)` |
| `EditPage` | `getHeader(R)`, `getFormActions(R)` |
| `ViewPage` | `getHeader(R, record)`, `getActions(R, recordId, basePath)` |

`getHeaderActions` / `getRowActions` / `getActions` all return `[]` by default — Filament-style explicit. Use the pre-built factories to opt in:

```ts
class ListArticles extends ListPage {
  static override getResource() { return ArticleResource }
  static override getHeaderActions(R, basePath) {
    return [Action.create(R, basePath)]
  }
  static override getRowActions(R, basePath) {
    return [Action.edit(R, basePath), Action.delete(R, basePath)]
  }
}

class ViewArticle extends ViewPage {
  static override getResource() { return ArticleResource }
  static override getActions(R, recordId, basePath) {
    if (!recordId) return []
    return [Action.edit(R, basePath, recordId), Action.delete(R, basePath, recordId)]
  }
}
```

Factory shapes: `Action.create(R, base)`, `Action.edit(R, base, recordId?)`, `Action.view(R, base, recordId?)`, `Action.delete(R, base, recordId?)`. `recordId` baked at config time (view-page context) vs `:id` template (row context).

## Globals

Panels and pilotiq both have `Global` for singleton resources (site settings, brand config). The migration is the same shape as `Resource`: `fields()` becomes `static form(form)`, validation is the same, but the routing changes from `/{panel}/globals/{slug}` to `{base}/{slug}` (no `/globals` segment).

```ts
// pilotiq
import { Global, Form, TextField } from '@pilotiq/pilotiq'

export class SiteSettings extends Global {
  static override label         = 'Site Settings'
  static override slug          = 'settings'
  static override model         = SiteSettingsModel

  static override form(form: Form): Form {
    return form.schema([
      TextField.make('siteName').required(),
      TextField.make('contactEmail').validate(email()),
    ])
  }
}
```

Register via `.globals([SiteSettings])` on the panel builder.

## Filters

Panels had `SelectFilter` only. Pilotiq adds `BooleanFilter` and the abstract `Filter` base for custom filters.

```ts
// pilotiq
import { SelectFilter, BooleanFilter } from '@pilotiq/pilotiq'

table.filters([
  SelectFilter.make('status').options([
    { label: 'Draft',     value: 'draft' },
    { label: 'Published', value: 'published' },
  ]),
  BooleanFilter.make('featured').label('Featured only'),
])
```

Active values come from URL query keys matching the filter name. Custom logic via `Filter.query((query, value) => …)`.

## List-page tabs

Pilotiq adds a Filament-style query-shortcut strip above resource list pages — "All / Drafts / Published / Archived"-style tabs, each narrowing the table query and showing an optional count badge. Tabs are the primary axis (status/type); filters refine within the active tab.

Override `getTabs()` on a `ListPage` subclass:

```ts
import { ListPage, ListTab, Action } from '@pilotiq/pilotiq'
import { ArticleResource } from './ArticleResource.js'

export class ListArticles extends ListPage {
  static override getResource() { return ArticleResource }

  static override getTabs() {
    return [
      ListTab.make('all').label('All'),
      ListTab.make('drafts')
        .label('Drafts')
        .badgeColor('warning')
        .badge(async () => prisma.article.count({ where: { status: 'draft' } }))
        .modifyQuery(q => q.where('status', 'draft')),
      ListTab.make('published')
        .label('Published')
        .badgeColor('success')
        .badge(async () => prisma.article.count({ where: { status: 'published' } }))
        .modifyQuery(q => q.where('status', 'published')),
    ]
  }
}
```

Builder surface: `.label()`, `.icon()`, `.badge(string | () => Promise<string|number|undefined>)`, `.badgeColor()`, `.default()`, `.modifyQuery((q: ModelQuery) => q)`, `.modifyContext((ctx: TableContext) => ctx)` (escape hatch for non-model `Table.records()` handlers).

- The active tab is carried in the URL as `?tab=name`; switching SPA-navigates and resets `page` to 1 while preserving `search`/`sort`/filter values.
- Default tab: `ListTab.default()` wins; otherwise the first tab.
- Badges resolve in parallel server-side (`Promise.all`); a thrown handler silently omits its badge rather than blanking the page.
- `modifyQuery` plugs into `modelTableRecords` next to `Filter.query()`, so tab predicates compose with active filters and search.
- The form-side `Tab` (under `Tabs.make().tabs([Tab.make('Profile')…])`) is a different class — it holds form children. List-page tabs use `ListTab` to disambiguate.

> Panels had no equivalent — list pages were unstructured and you'd build status filters by hand. The tab strip is a new affordance, not a 1:1 port.

## Actions

The `Action` primitive in pilotiq has four mutually-exclusive modes:

| Style | Builder | Use case |
|---|---|---|
| Link | `Action.href(url)` | Edit (link to edit page) |
| Form | `Action.method('post' \| 'delete' \| …).action(url)` | Delete (POSTs to delete endpoint) |
| Handler | `Action.handler(async (ctx) => …)` | Server-side custom action (publish, archive, etc.) |
| Submit | `Action.submit().form(formId)` | Form-submit button (default Save) |

Placement is one of `inline`, `bulk`, `row`, `header`. Bulk actions auto-add a checkbox column. Handler-style actions get a `dispatchUrl` stamped at render time and POST `{ ids?, ...values }` to the dispatcher.

Confirm prompts now render a styled Dialog (no more `window.confirm`). Set with `Action.confirm({ title?, message })`.

```ts
// pilotiq
Action.make('publish')
  .label('Publish')
  .placement('row')
  .handler(async (ctx) => {
    await ctx.record!.update({ status: 'published' })
  }),

Action.make('delete')
  .label('Delete')
  .destructive()
  .confirm({ message: 'Delete this article?' })
  .method('delete')
  .action(`${basePath}/articles/:id/delete`),
```

## Theme + branding

Theme config moves from panel-level to pilotiq builder-level:

```ts
// pilotiq
Pilotiq.make('Admin')
  .path('/admin')
  .branding({ name: 'Acme', logo: '/logo.svg' })
  .theme({ preset: 'default', accentColor: 'terracotta' })
  .resources([…])
```

For the in-browser theme editor (live preview, persisted to DB), opt in via the plugin:

```ts
import { themeEditor } from '@pilotiq/pilotiq/plugins'

Pilotiq.make('Admin').use(themeEditor()).resources([…])
```

## Step-by-step migration order

For each resource, do them in this order — earlier steps unblock later ones, and you can run panels and pilotiq side-by-side until cutover:

1. **Resource shell** — copy the class, change `fields()` → `static form()`, split visible columns into `static table()` with `Column.make()` calls.
2. **Filters** — move from `filters()` to `table().filters([…])`.
3. **Actions** — move from `actions()` to inline-on-Form / inline-on-Table / page-header actions.
4. **Validation** — keep as-is; Field.validate() works the same.
5. **Rich text** — swap `RichContentField` for `RichTextField` from `@pilotiq/tiptap`. Translate any custom `Block` definitions (the builder API is the same shape).
6. **Custom pages** — only if you had custom panels page overrides. Otherwise skip.
7. **Wire** — register on the panel builder, add the `pilotiq()` Vite plugin, swap the provider call.
8. **Delete** — once the resource works in pilotiq, delete the panels copy.

## Things that aren't ported (yet)

- **Live updates** (`static live = true`) — not implemented in pilotiq yet.
- **Versioning** (`static versioned = true`) — not implemented.
- **Draft/publish workflow** (`static draftable = true`) — model-side, currently up to the user.
- **Soft deletes UI** (trash & restore) — works at the model layer but no built-in UI yet.
- **Autosave + draft recovery** — not implemented.
- **Per-resource agents** — not part of free pilotiq.

These were all panels features. They'll either land in pilotiq later or stay panels-only until removal.
